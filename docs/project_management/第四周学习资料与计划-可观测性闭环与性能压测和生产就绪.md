## 第 1 章：前置知识准备

在开始本周工作之前，需要掌握以下可观测性、性能测试与混沌工程基础概念。

### P0：RED 方法论与 USE 方法论

**RED 方法论**（Tom Wilkie 提出）面向请求驱动型服务，关注三个核心指标：

| 指标 | 含义 | Prometheus 类型 | 本项目实现 |
|---|---|---|---|
| **Rate** | 每秒请求数 | Counter | `privshield_requests_total` |
| **Errors** | 每秒错误数 | Counter | `privshield_requests_total{status=~"5.."}` |
| **Duration** | 请求延迟分布 | Histogram | `privshield_request_duration_seconds` |

**USE 方法论**（Brendan Gregg 提出）面向资源型组件，关注三个维度：

| 维度 | 含义 | 本项目关注点 |
|---|---|---|
| **Utilization** | 资源使用率 | CPU / 内存 / 磁盘 / 连接池 |
| **Saturation** | 资源饱和度 | 队列深度 / 信号量占用 / 刷盘器积压 |
| **Errors** | 资源错误数 | 写入失败 / 连接超时 / 熔断器状态 |

**本项目指标体系**：
- `pkg/observability/REDMetrics` — 传输层通用请求指标（中间件自动埋点）
- `pkg/metrics/Collector` — 业务领域多维指标（Handler 显式上报）
- 二者互补而非替代

### P1：OpenTelemetry 分布式追踪模型

**OpenTelemetry (OTel)** 是 CNCF 的可观测性标准框架，提供统一的追踪、指标、日志 API。

**核心概念**：

| 概念 | 说明 | 本项目实现 |
|---|---|---|
| Trace | 一次完整请求的调用链 | BFF → Hub → Engine → Audit |
| Span | 调用链中的一个工作单元 | 每个服务/阶段创建子 Span |
| SpanContext | 跨进程传播的追踪上下文 | W3C TraceContext (`traceparent`) |
| Exporter | Span 数据导出目标 | OTLP → Jaeger/Tempo |

**本项目的 Tracer 接口**：

```go
// Tracer 是抽象分布式追踪接口
type Tracer interface {
    StartSpan(ctx context.Context, name string, attrs map[string]string) (context.Context, func())
}
```

**当前状态**：
- `NoOpTracer`：默认空操作，零开销
- `OTelTracer`：占位实现，待引入 OTel SDK 后完善
- 通过 `atomic.Pointer[Tracer]` 实现无锁安全读写

### P2：Prometheus 指标类型与查询语言

| 指标类型 | 用途 | 示例 |
|---|---|---|
| Counter | 单调递增计数器 | `privshield_requests_total` |
| Gauge | 可增可减的当前值 | `privacy_gateway_healthy_nodes` |
| Histogram | 分布统计（分桶） | `privshield_request_duration_seconds` |
| Summary | 分位数计算 | 客户端计算的 P99 |

**常用 PromQL 查询**：

```promql
# 每秒请求率（5 分钟窗口）
sum(rate(privshield_requests_total[5m])) by (endpoint)

# P95 延迟
histogram_quantile(0.95, sum(rate(privshield_request_duration_seconds_bucket[5m])) by (le))

# 5xx 错误率
sum(rate(privshield_requests_total{status=~"5.."}[5m])) / sum(rate(privshield_requests_total[5m]))
```

### P3：Grafana 仪表盘设计原则

**四层仪表盘模型**：

| 层级 | 关注点 | 受众 |
|---|---|---|
| Golden Signals | 延迟/流量/错误/饱和度 | On-Call 快速定位 |
| Service Topology | 服务依赖与调用链 | 架构师 |
| Resource Health | CPU/内存/磁盘/网络 | 运维 |
| Business Metrics | 脱敏量/分类命中率/预算消耗 | 业务方 |

- `deploy/grafana/service-hub-dashboard.json` — 调度中枢专项（流水线阶段/任务状态/租约深度）

### P4：性能压测方法论与梯度加压

**梯度加压法**：从低 QPS 开始，逐步增加负载，观察系统行为变化。

| 阶段 | 目标 | 关注指标 |
|---|---|---|
| 基线测量 | 确定空载/轻载性能 | P50/P95/P99 延迟 |
| 梯度加压 | 找到 QPS 拐点 | P99 延迟急升点 |
| 极限压测 | 确定系统上限 | 最大 QPS / 错误率 |
|  soak test | 检测内存/资源泄漏 | 长时间运行的内存曲线 |

**压测工具选型**：

| 工具 | 适用场景 | 特点 |
|---|---|---|
| `hey` | 简单 HTTP 压测 | 轻量、易上手 |
| `wrk` | 高性能 HTTP 压测 | Lua 脚本、高并发 |
| `Locust` | 分布式场景压测 | Python 脚本、模拟用户行为 |
| `vegeta` | 梯度加压 | 自动速率调节 |

### P5：混沌工程核心概念

**混沌工程四原则**（Netflix Chaos Engineering）：

1. **建立稳定假设**：定义系统在正常状态下的行为
2. **引入真实事件**：模拟生产环境中可能发生的事件
3. **在生产环境运行**：在真实环境中进行实验
4. **最小化影响**：控制爆炸半径

**本项目演练场景**：

| 场景 | 注入方式 | 预期行为 |
|---|---|---|
| 节点宕机 | `kill -9` | 任务重试 / 刷盘器暂存 |
| 网络分区 | `iptables` / `tc` | BFF 降级响应 |
| 存储故障 | 停止 PostgreSQL | 降级到 SQLite |
| 慢依赖 | `tc netem delay` | 超时控制 / 熔断器触发 |
| 刷盘器饱和 | 持续高速写入 | `ErrBacklogSaturated` 快速拒绝 |
| 熔断器触发 | 模拟下游 5xx | Closed → Open → HalfOpen |
| 隐私预算耗尽 | 连续 DP 查询 | 预算拒绝后续请求 |

### 2.2 Prometheus RED 指标体系

`pkg/observability/metrics.go` 实现了标准的 RED 指标集：

```go
type REDMetrics struct {
    registry        *prometheus.Registry
    RequestsTotal   *prometheus.CounterVec    // 请求计数（protocol/endpoint/status）
    RequestDuration *prometheus.HistogramVec  // 请求延迟直方图（protocol/endpoint）
}
```

**指标命名规范**：
- `privshield_requests_total` — 请求总数
- `privshield_request_duration_seconds` — 请求延迟

**自动埋点中间件**：

```go
// PrometheusMiddleware 自动记录 HTTP 请求 RED 指标
func (m *REDMetrics) PrometheusMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        start := time.Now()
        c.Next()
        // 豁免 /metrics 端点自身（避免自抓取导致指标无限自增）
        if path == "/metrics" { return }
        duration := time.Since(start).Seconds()
        m.RecordRequest("http", path, c.Writer.Status(), duration)
    }
}
```

**gRPC 拦截器**：

```go
func (m *REDMetrics) UnaryServerInterceptor() grpc.UnaryServerInterceptor {
    return func(ctx context.Context, req any, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
        start := time.Now()
        resp, err := handler(ctx, req)
        duration := time.Since(start).Seconds()
        statusCode := 0
        if err != nil { statusCode = int(status.Code(err)) }
        m.RecordRequest("grpc", info.FullMethod, statusCode, duration)
        return resp, err
    }
}
```

### 2.3 分布式追踪 Tracer 接口设计

`pkg/observability/tracing.go` 定义了抽象追踪接口：

```go
type Tracer interface {
    StartSpan(ctx context.Context, name string, attrs map[string]string) (context.Context, func())
}
```

**实现层次**：

| 实现 | 场景 | 开销 |
|---|---|---|
| `NoOpTracer` | 默认 / 未配置 OTLP 端点 | 零 |
| `OTelTracer` | 配置了 OTLP 导出端点 | 当前降级为 NoOp（占位） |

**初始化流程**：

```go
func InitTracing(endpoint, serviceName string) Tracer {
    tracerOnce.Do(func() {
        if endpoint == "" {
            endpoint = os.Getenv("OTEL_EXPORTER_OTLP_ENDPOINT")
        }
        if endpoint != "" {
            t = &OTelTracer{Endpoint: endpoint, ServiceName: serviceName}
        } else {
            t = &NoOpTracer{}
        }
        tracer.Store(&t)
    })
}
```

**关键设计**：
- `sync.Once` 保证仅初始化一次
- `atomic.Pointer[Tracer]` 保证无锁安全读写
- `ResetTracing()` 仅限测试使用

### 2.5 Prometheus 告警规则深度走读

`deploy/prometheus/alerts.yml`（314 行）定义了 6 大类告警规则：

#### 可用性告警（PrivShield.availability）

#### 延迟告警（PrivShield.latency）

| 告警 | 条件 | 严重度 | 持续时间 |
|---|---|---|---|
| `HighRequestLatencyP95` | P95 > 1s | warning | 5m |
| `HighGatewayLatencyP95` | P95 > 2s | warning | 5m |
| `HighClassificationLatency` | P95 > 5s | warning | 5m |

#### 错误告警（PrivShield.errors）

| 告警 | 条件 | 严重度 | 持续时间 |
|---|---|---|---|
| `HighGatewayErrorRate` | 5xx > 5% | critical | 5m |
| `HighAuthDenialRate` | 认证拒绝 > 10% | warning | 5m |
| `HighGatewayRetryRate` | 重试率 > 10% | warning | 5m |

#### 隐私预算告警（PrivShield.privacy）

| 告警 | 条件 | 严重度 | 说明 |
|---|---|---|---|
| `PrivacyBudgetNearlyExhausted` | 剩余 < 0.1 | warning | 预算即将耗尽 |
| `PrivacyBudgetExhausted` | 剩余 <= 0 | critical | 所有 DP 查询被拒绝 |

#### 服务告警（PrivShield.services）

| 告警 | 目标服务 | 条件 | 严重度 |
|---|---|---|---|

| `ServiceHubAgentCallFailure` | service-hub → agent | 失败率 > 5% | critical |
| `AuditLogWriteFailure` | audit-log | 写入失败 > 5% | critical |

#### 安全告警（PrivShield.security）— 三级等保 G-09

| 告警 | 条件 | 攻击类型 |
|---|---|---|
| `BruteForceDetected` | 单 IP 认证失败 > 0.5/s | 暴力破解 |
| `AccountLockoutSurge` | 账号锁定 > 3/s | 凭证攻击 |

## 第 4 章：Day 4 混沌工程故障注入演练

### 4.1 混沌工程方法论

**演练原则**：
1. 每次演练只注入一个故障（隔离变量）
2. 演练前定义预期行为（稳定假设）
3. 演练中实时监控关键指标
4. 演练后对比预期与实际行为
5. 发现缺陷立即记录并修复

### 4.2 演练场景 1：节点宕机

**注入方式**：`kill -9 <engine-go-pid>`

**预期行为**：
- service-hub 任务重试（`ClassDownstream` 可重试）
- audit-log BufferedAuditStore 重试暂存区保留
- 网关 P2C-EWMA 自动摘除故障节点
- 恢复后自动重新加入

**验证步骤**：
1. 启动全栈服务
2. 发送持续请求（`vegeta attack -rate 50 -duration 300s`）
3. 第 60 秒 `kill -9` 一个 engine-go 实例
4. 观察：错误率短暂上升后恢复
5. 第 120 秒重启 engine-go
6. 观察：流量自动回灌

### 4.3 演练场景 2：网络分区

**注入方式**：`iptables -A OUTPUT -d <audit-log-ip> -j DROP`

**预期行为**：
- BFF 层降级响应（fallback 数据）
- service-hub 存证提交失败 → 任务 failed（P0-6）
- 网络恢复后 service-hub 自动重试

**验证步骤**：
1. 注入网络分区（BFF → audit-log）
2. 观察 BFF 返回降级数据（`source: "fallback"`）
3. 恢复网络
4. 观察服务自动恢复

### 4.4 演练场景 3：存储故障

**注入方式**：停止 PostgreSQL 容器 `docker stop postgres`

**预期行为**：
- audit-log 降级到 SQLite
- 若 SQLite 也不可用，降级到内存存储
- `StrictStorage=true` 时直接拒绝服务

**验证步骤**：
1. 配置 PostgreSQL 为主存储
2. 停止 PostgreSQL
3. 观察 audit-log 日志中的降级消息
4. 验证审计写入仍然成功（SQLite 兜底）
5. 重启 PostgreSQL
6. 观察服务自动切回 PostgreSQL

### 4.5 演练场景 4：慢依赖

**注入方式**：`tc qdisc add dev eth0 root netem delay 10000ms`

**预期行为**：
- engine-go 响应延迟 10s
- service-hub 超时控制生效（15s classify 超时）

**验证步骤**：
1. 在 engine-go 容器注入 10s 延迟
2. 观察 service-hub 任务失败率上升
3. 观察熔断器状态变化（`privacy_circuit_breaker_state`）
4. 移除延迟
5. 观察熔断器恢复（HalfOpen → Closed）

### 4.6 演练场景 5：刷盘器饱和

**注入方式**：持续高速写入审计日志

**预期行为**：
- 队列深度持续增长
- 达到 `BufferSize`（10000）后 `ErrBacklogSaturated` 快速拒绝

**验证步骤**：
1. 停止底层存储（模拟写入极慢）
2. 持续高速写入审计日志

### 4.7 演练场景 6：熔断器触发

**注入方式**：模拟下游持续返回 5xx

## 第 6 章：可观测性代码深度走读

### 6.1 REDMetrics 指标注册与中间件

`REDMetrics` 使用独立的 `prometheus.Registry`，避免与默认注册表冲突：

```go
func NewREDMetrics() *REDMetrics {
    reg := prometheus.NewRegistry()  // 独立注册表
    m := &REDMetrics{
        registry: reg,
        RequestsTotal: prometheus.NewCounterVec(...),
        RequestDuration: prometheus.NewHistogramVec(...),
    }
    reg.MustRegister(m.RequestsTotal, m.RequestDuration)
    return m
}
```

**设计要点**：
- 独立注册表支持多模块共存（各服务使用各自的指标前缀）
- `MustRegister` 允许追加注册自定义指标
- `/metrics` 端点豁免自动埋点（避免自抓取导致指标无限自增）

### 6.2 Collector 业务指标收集器

`pkg/metrics/Collector` 在 RED 基础上扩展业务指标：

| 指标 | 类型 | 说明 |
|---|---|---|
| `privacy_requests_total` | Counter | 隐私请求总数（按操作/状态分） |
| `privacy_classification_total` | Counter | 分类结果计数（按级别/方法分） |
| `privacy_budget_remaining` | Gauge | 隐私预算剩余 |
| `privacy_circuit_breaker_state` | Gauge | 熔断器状态（0=closed, 1=open, 2=halfopen） |
| `privacy_gateway_healthy_nodes` | Gauge | 网关健康后端数 |

### 6.3 Tracer 接口与 NoOp/OTel 实现

**接口设计**：

```go
type Tracer interface {
    StartSpan(ctx context.Context, name string, attrs map[string]string) (context.Context, func())
}
```

**返回值语义**：
- `context.Context`：携带 Span 上下文的副本（用于传播到子调用）
- `func()`：Span 结束回调（调用方必须在 Span 结束时调用）

**NoOp 实现**：直接返回原上下文与空回调，零开销。

**OTel 占位实现**：当前降级为 NoOp，待引入 `go.opentelemetry.io/otel` SDK 后创建真实 Span。

### 6.4 RequestLogger 结构化日志中间件

### 6.6 分布式追踪传播链路深度分析

#### 6.6.1 追踪 ID 生成算法

`GenerateRequestID` 生成包含高精度时间戳与加密级随机数的唯一追踪 ID：

```go
func GenerateRequestID() string {
    var buf [4]byte
    _, _ = rand.Read(buf[:])  // crypto/rand 4 字节安全随机数
    return "req-" + strings.Replace(
        time.Unix(0, time.Now().UnixNano()).Format("20060102150405.000000000"),
        ".", -, 1,
    ) + "-" + hex.EncodeToString(buf[:])
}
```

**格式规范**：`req-<YYYYMMDDHHMMSS>-<纳秒>-<8位十六进制随机数>`

示例：`req-20260903103000-123456789-a1b2c3d4`

**碰撞概率分析**：
- 时间戳精度：纳秒级（保证同纳秒内唯一）
- 随机分量：4 字节 = 32 位 = ~42 亿种组合
- 同纳秒碰撞概率：1/2^32 ≈ 2.3×10⁻¹⁰（可忽略）

#### 6.6.2 TraceMiddleware 追踪上下文传播

`TraceMiddleware` 实现 4 级防空兜底的追踪 ID 提取与传播：

```go
func TraceMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        var traceID string

        // 第 1 级：复用上游 RequestID() 中间件已生成的 request_id
        if rid, exists := c.Get("request_id"); exists { ... }

        // 第 2 级：读取客户端传入的 X-Request-ID 请求头
        if traceID == "" {
            traceID = c.GetHeader(TraceHeader)
        }

        // 第 3 级：自动生成唯一 TraceID
        if traceID == "" {
            traceID = GenerateRequestID()
        }

        // 双键名存储（向后兼容 + 专属键）
        c.Set("request_id", traceID)
        c.Set(TraceIDContextKey, traceID)

        // 双头部响应（X-Request-ID + X-Trace-ID）
        c.Header(TraceHeader, traceID)
        c.Header(TraceIDHeader, traceID)

        // 注入 request.Context() 供下游客户端自动透传
        ctx := ContextWithRequestID(c.Request.Context(), traceID)
        c.Request = c.Request.WithContext(ctx)

        c.Next()
    }
}
```

**传播链路图**：

```
客户端 → [X-Request-ID] → TraceMiddleware
                              ↓
                    ┌─── gin.Context ───┐
                    │  request_id (兼容) │
                    │  PrivShield-Trace-ID │
                    └───────────────────┘
                              ↓
                    ┌─── request.Context() ───┐
                    │  requestIDKeyType (私有)  │
                    └──────────────────────────┘
                              ↓
              下游 HTTP/gRPC 客户端自动提取
              → 注入 X-Request-ID 出站到下一跳
```

#### 6.6.3 Context 传播的私有键类型

```go
type requestIDKeyType struct{}  // 私有类型，防止跨包冲突
var requestIDKey requestIDKeyType
```

使用未导出的 struct 类型作为 context key 是 Go 最佳实践：
- 外部包无法构造相同类型的键，避免键冲突
- 空 struct 不占内存（零大小）
- 配合 `ContextWithRequestID` / `RequestIDFromContext` 提供类型安全的读写

## 第 11 章：常见问题与排查指南

### 11.1 可观测性问题

#### 问题 1：Prometheus 无法抓取指标

**症状**：Prometheus targets 页面显示 DOWN

**排查步骤**：
1. 确认 `/metrics` 端点可访问：`curl http://<service>:<port>/metrics`
2. 检查 Prometheus 目标状态：`http://prometheus:9090/targets`
3. 检查网络策略 / 防火墙规则
4. 检查 TLS 配置（ServiceMonitor 是否配置了 `insecureSkipVerify`）
5. 检查服务是否监听在 `0.0.0.0`（而非 `127.0.0.1`）

**常见原因**：
- 服务监听在 `127.0.0.1`，Prometheus 在另一个容器中无法访问
- TLS 开启但 ServiceMonitor 未配置 HTTPS scheme
- NetworkPolicy 阻止了 Prometheus Pod 的访问

#### 问题 2：Grafana 仪表盘无数据

**症状**：面板显示 "No data"

**排查步骤**：
1. 确认 Prometheus 数据源配置正确
2. 检查 PromQL 查询中的指标名称是否匹配（`privshield_` vs `privacy_` 前缀）
3. 检查时间范围是否包含数据点
4. 确认 Prometheus 已成功抓取至少一个 scrape interval
5. 检查指标标签是否与查询中的标签匹配

### 11.2 性能问题

#### 问题 3：压测时错误率飙升

**症状**：QPS 超过某阈值后错误率急剧上升

**排查步骤**：
1. 检查是否触发限流：`rate(privshield_requests_total{status="429"}[1m])`
2. 检查是否触发并发上限：`service-hub` 的 `taskSem` 信号量（最大 10）
3. 检查下游超时配置：Agent 客户端默认超时
4. 检查连接池是否耗尽：PostgreSQL `max_connections`
5. 检查内存是否触顶：`go_memstats_alloc_bytes`

**常见原因**：
- 限流配置过低（`PRIVACY_RATE_LIMIT_DEFAULT_RPS`）
- Hub 并发信号量饱和（`taskSem` 最大 10）
- PostgreSQL 连接池耗尽（`SERVICE_HUB_PG_MAX_CONNS`）

#### 问题 4：内存泄漏

**症状**：内存使用量持续增长，不随 GC 回收

**排查步骤**：
1. 启用 pprof：`PRIVACY_PPROF_ENABLED=true`
2. 抓取堆快照：`go tool pprof http://localhost:8079/debug/pprof/heap`
3. 对比两次快照差异：`go tool pprof --base old.prof new.prof`
4. 检查 Goroutine 泄漏：`/debug/pprof/goroutine?debug=2`

### 11.3 混沌恢复问题

#### 问题 5：混沌演练后服务未自动恢复

**症状**：故障注入结束后服务仍返回错误

**排查步骤**：
1. 检查熔断器是否仍处于 Open 状态：`privacy_circuit_breaker_state`
2. 检查 HalfOpen 探测是否成功：查看服务日志
3. 检查服务健康检查端点：`/health`、`/readyz`
4. 查看服务日志中的错误信息：`slog` JSON 日志
5. 检查 DNS 解析是否恢复（容器网络场景）

**常见原因**：
- 熔断器 Open 后 HalfOpen 探测间隔过长
- 后端服务虽然恢复但 DNS 缓存未更新
- 健康检查失败阈值设置过高

### 11.4 部署问题

#### 问题 6：Helm 部署失败

**症状**：`helm install` 报错

**排查步骤**：
1. `helm template` 检查渲染结果：`helm template my-release ./deploy/helm/PrivShield`
2. `helm lint` 检查 Chart 语法
3. 检查 values 覆盖优先级（`--set` > `-f` > `values.yaml`）
4. 检查 Secret 是否已创建：`kubectl get secrets -n privshield`

#### 问题 7：容器启动失败（Fail-Closed 门禁）

**症状**：容器启动后立即退出

**排查步骤**：
1. 查看容器日志：`docker logs <container>`
2. 检查必填环境变量是否已配置（`:?` 变量）
3. 检查证书文件是否存在且权限正确
4. 检查 `STRICT_STORAGE` 是否导致拒绝启动（存储不可用时）

**常见 Fail-Closed 门禁**：
- 非环回监听 + 无 API Key → 拒绝启动
- `REQUIRE_TLS=true` + `TLS_ENABLED=false` → 拒绝启动
- gRPC TLS 启用 + 无 CN 白名单 → 拒绝启动
- audit-log 缺少加密密钥或哈希密钥 → 拒绝启动
