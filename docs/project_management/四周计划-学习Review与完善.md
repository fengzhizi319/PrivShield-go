# PrivShield 四周学习、Review 与完善计划

> 本计划面向 AI 生成代码的人工 Review、学习与改进阶段。代码整体已由 AI 完成，但尚未经过系统性的人工审查与生产级打磨。
>
> 服务分级：
> - 商业应用版（生产级标准）：engine-go、services/audit-log、services/service-hub
> - 辅助测试版（基本功能可用）：services/datasource-mgr、console/app-lz

---

## 总体目标

通过四周时间，完成以下转变：

- 从"AI 生成可运行"到"人工理解可维护"
- 从"功能跑通"到"生产级健壮"
- 从"单服务可用"到"全链路协同"
- 从"基础安全"到"零信任合规"

## 第一周：核心引擎深度 Review 与安全加固

> 聚焦 engine-go 核心模块，逐行理解实现细节，补齐安全与可观测性短板。

### Day 1-2：网关与流量治理 Review

**审查重点**

审查 `engine-go/internal/gateway/` 下所有文件，重点理解：

- P2C-EWMA 负载均衡算法的实现正确性与边界条件
- 熔断器三态转换逻辑（Closed -> Open -> HalfOpen）的竞态安全性
- HTTP 反向代理的 BufferPool 零分配机制是否真正无泄漏
- gRPC 透明代理的 RawCodec 编解码与连接池管理
- 后端 TLS 构建（`backend_tls.go`）的证书校验链完整性

**发现的问题与改进方向**

- 当前限流完全基于内存（32 分片令牌桶），缺少 Redis 分布式限流适配器。需要为多实例部署场景补充 Redis 滑动窗口限流驱动
- 连接池配置（Max 256）在高并发场景下是否足够，需压测验证
- 熔断器冷却时间硬编码，应支持配置化

**改进任务**

- 为 `http_proxy.go` 和 `grpc_proxy.go` 补充边界条件测试（后端全部不可用、超时、连接重置）
- 实现 Redis 分布式限流适配器（基于 Lua 脚本保证原子性），与现有限流中间件对接
- 熔断器参数（阈值、冷却时间、半开探测数）抽取为可配置项

### Day 3-4：安全体系 Review（mTLS、认证、权限）

**审查重点**

审查 `engine-go/internal/security/` 全部文件，重点理解：

- mTLS CN 白名单热重载机制（5s 节流、两阶段提交）的正确性
- API Key 常量时间比较是否覆盖所有分支
- 权限模型（scope-based）的完整性，`identity.go` 中 REST 路径与 gRPC 方法的权限映射
- 安全头中间件（CSP、HSTS 等）的覆盖范围

**发现的问题与改进方向**

- mTLS CN 白名单配置字段存在（`MTLSEnabled`、`MTLSAllowedCNs`），但未接入主中间件链，请求级 CN 校验未生效
- 权限模型为静态 scope 定义，无动态 RBAC 后端，缺少角色继承与权限组概念
- API Key 无轮转机制，过期策略缺失
- 缺少 OAuth2/JWT 支持，无法对接企业统一认证

**改进任务**

- 将 mTLS CN 校验接入 Gin 中间件链，确保启用 mTLS 时每个请求都验证客户端证书 CN
- 补充权限模型文档，明确每个 REST 端点和 gRPC 方法所需的 scope
- 实现 API Key 过期时间字段与过期检查逻辑
- 为 `auth.go` 补充并发安全测试（多 goroutine 同时验签）

### Day 5：可观测性 Review（日志、指标、追踪）

**审查重点**

审查 `engine-go/internal/observability/` 全部文件，重点理解：

- `EngineMetrics` 与 `pkg/observability.REDMetrics` 的继承关系
- Prometheus 指标命名规范（是否符合 Prometheus 命名约定）
- 追踪_span_创建的完整性（是否覆盖所有关键路径）
- 结构化日志字段一致性（是否包含 trace_id、span_id、request_id）

**发现的问题与改进方向**

- 追踪模块（`tracing.go`）仅为 `pkg/observability` 的薄封装，引擎内部未创建任何引擎特定的 Span（如分类漏斗各阶段、预算扣减）
- 日志虽为结构化 JSON，但审计关键事件（预算耗尽、分类命中 LLM、熔断器状态变更）未输出标准化审计日志
- 缺少 SLO 告警规则定义

**改进任务**

- 在分类漏斗（Rule -> NER -> LLM）每个阶段创建独立 Span，形成可观测的调用链火焰图
- 为熔断器状态变更、预算耗尽、mTLS 证书即将过期等关键事件添加结构化审计日志
- 补充 Prometheus 告警规则（`deploy/prometheus/rules/`），覆盖：P99 延迟 > 5s、错误率 > 1%、熔断器 Open、预算消耗 > 80%

## 第二周：商业服务深度 Review 与生产级加固

> 聚焦 services/audit-log 和 services/service-hub，按商业交付标准逐项审查与加固。

### Day 1-2：audit-log 审计日志服务 Review

**审查重点**

审查 `services/audit-log/` 全部源码，重点理解：

- 分层存储架构（PostgreSQL > SQLite > 内存）的降级逻辑与数据一致性
- HMAC-SM3 证据链签名的实现（是否覆盖所有审计字段，防篡改校验流程）
- 微批刷写器（micro-batch flusher）的刷写间隔、批量大小与优雅停机
- 加密归档段（encrypted archive segments）的密钥管理与解密恢复流程
- 写入-only Postgres 角色的自检机制

**发现的问题与改进方向**

- 需确认 HMAC-SM3 签名是否覆盖审计条目的所有关键字段（时间戳、操作类型、操作者、数据指纹）
- 归档加密密钥目前来源需明确（是否走 KMS）
- 微批刷写器的优雅停机是否保证零数据丢失（flush 超时处理）
- 缺少审计日志查询 API 的分页与过滤能力

**改进任务**

- 逐行审查 HMAC-SM3 签名逻辑，确保签名覆盖完整且校验流程可独立验证
- 归档加密密钥对接环境变量注入（预留 KMS 接口）
- 为微批刷写器补充优雅停机测试（发送 SIGTERM 后验证所有缓冲数据已落盘）
- 实现审计日志查询 API 的分页（cursor-based）与时间范围过滤

### Day 3-4：service-hub 服务调度中枢 Review

**审查重点**

审查 `services/service-hub/` 全部源码，重点理解：

- 流水线调度模型（任务创建 -> 分发 -> 执行 -> 回调）的状态机完整性
- 租约任务存储（leased task store）的租约过期与抢占机制
- 崩溃恢复（crash recovery）的触发条件与恢复策略
- 后台定期重试（periodic background retry）的重试策略与退避算法
- 审计日志证据绑定（P0-6 audit-log evidence binding）的实现

**发现的问题与改进方向**

- 租约过期后的任务重新调度是否存在竞态（多副本同时抢占）
- 崩溃恢复是否覆盖所有任务状态（进行中、已暂停、超时）
- 重试策略是否区分可重试错误（网络超时）与不可重试错误（参数错误）
- 数据保留清理（data retention cleanup）的安全边界（是否可能误删未完成任务）

**改进任务**

- 为租约抢占逻辑补充并发测试（模拟多副本同时检测到租约过期）
- 崩溃恢复增加状态检查清单，确保仅恢复"进行中"和"已暂停"任务
- 重试策略引入错误分类（retryable vs non-retryable），避免无意义重试
- 数据保留清理增加安全断言：仅清理终态（成功/失败/已取消）且超过保留期的任务

### Day 5：跨服务集成与端到端联调

**任务内容**

- 启动全栈服务（engine-go + audit-log + service-hub + datasource-mgr + app-lz），验证端到端流程
- 测试 service-hub 调度脱敏任务 -> engine-go 执行 -> audit-log 记录审计日志的完整链路
- 验证 audit-log 证据链签名在跨服务传递过程中的完整性
- 检查 app-lz BFF 层对四个上游服务的聚合代理是否正确（超时传递、错误码映射、响应合并）

**改进任务**

- 补充全栈集成测试（`tests/e2e/`），覆盖核心业务流程
- 统一各服务的错误码体系（确保同一业务错误在不同服务中返回一致的错误码）
- app-lz BFF 层补充上游服务健康检查聚合（任一上游不可用时返回降级响应而非 502）

## 第三周：存储韧性、任务可靠性与全链路可观测

> 聚焦存储层健壮性、任务执行可靠性与全链路可观测性闭环。

### Day 1-2：存储层 Review 与韧性加固

**审查重点**

审查所有存储相关实现：

- engine-go 的隐私预算存储（当前为纯内存 `budget.BudgetAccountant`）
- audit-log 的分层存储降级逻辑
- service-hub 的租约任务存储
- datasource-mgr 的 CSV 数据加载（`yibao.csv`、`kangyang.csv`）

**发现的问题与改进方向**

- engine-go 的隐私预算完全存储在内存中，进程重启后预算数据丢失。`DeepHealthCheck` 报告 `budget_store` 组件健康，但实际仅为内存会计器
- 缺少预算持久化方案（Redis 或 SQLite/PostgreSQL）
- audit-log 的存储降级（PostgreSQL -> SQLite -> 内存）在降级过程中的数据一致性需验证
- datasource-mgr 的 CSV 加载缺少大文件保护（Zip bomb 类似的 CSV bomb）

**改进任务**

- 为 engine-go 实现隐私预算持久化驱动（优先 SQLite，预留 Redis 接口）
- audit-log 存储降级补充集成测试（模拟 PostgreSQL 不可用，验证降级到 SQLite 后数据不丢失）
- datasource-mgr CSV 加载增加文件大小限制与行数上限保护
- 所有存储层补充磁盘空间不足时的优雅降级处理

### Day 3-4：任务可靠性与韧性 Review

**审查重点**

审查 service-hub 的任务执行可靠性：

- 任务执行超时控制（context deadline 传递是否完整）
- 任务取消机制（已提交任务是否可取消，取消后资源是否释放）
- 任务优先级调度（是否存在饥饿风险）
- 幂等性保证（同一任务重复提交是否产生副作用）

**发现的问题与改进方向**

- 需确认任务执行超时后，下游 engine-go 的连接是否正确关闭（避免资源泄漏）
- 任务取消是否为最佳努力（best-effort）还是强保证
- 缺少任务执行进度的上报机制（长任务无法感知进度）
- 幂等性依赖调用方保证，服务端未做幂等键检查

**改进任务**

- 任务超时后增加下游连接强制关闭逻辑（`context.WithTimeout` 传递至 gRPC 调用）
- 实现任务进度上报接口（`UpdateTaskProgress`），支持长任务的进度百分比上报
- 引入幂等键（idempotency-key）机制，相同幂等键的任务在 24 小时内仅执行一次
- 补充任务可靠性测试（超时、取消、重复提交、下游不可用）

### Day 5：全链路可观测性闭环

**审查重点**

审查从客户端请求到最终响应的全链路追踪覆盖度：

- app-lz BFF 层是否生成或透传 W3C `traceparent`
- service-hub 调度任务时是否将 trace context 传递至 engine-go
- engine-go 内部各阶段（分类漏斗、预算扣减、脱敏执行）是否创建 Span
- audit-log 写入审计条目时是否关联 trace_id
- 所有 Span 是否正确上报至 OpenTelemetry Collector

**改进任务**

- app-lz BFF 层补充 trace context 生成与透传逻辑
- service-hub 任务调度时通过 gRPC metadata 传递 trace context
- engine-go 内部为分类漏斗三阶段（Rule -> NER -> LLM）创建子 Span
- audit-log 审计条目增加 `trace_id` 字段，支持从追踪系统跳转到审计日志
- 在 Grafana 中构建统一看板：展示请求链路（BFF -> Hub -> Engine -> Audit）的完整拓扑与耗时分布

## 第四周：性能压测、混沌演练与生产就绪

> 通过极限压测与故障注入验证系统韧性，完成生产就绪评审。

### Day 1-2：性能基线与极限压测

**压测计划**

- 使用 `hey` / `wrk` / `Locust` 对各服务进行梯度加压
- 压测场景覆盖：
  - engine-go 单接口脱敏（纯 CPU 计算型）
  - engine-go 分类漏斗（含 LLM 调用，IO 密集型）
  - service-hub 任务调度（高并发任务创建与查询）
  - audit-log 审计写入（高吞吐写入场景）
  - app-lz BFF 聚合代理（多上游并发调用）

**关注指标**

- QPS 吞吐拐点（P99 延迟开始急剧上升的临界点）
- 内存/CPU 使用率曲线（是否存在泄漏）
- 连接池利用率（是否出现连接等待）
- 熔断器触发频率（后端过载时的保护效果）

**改进任务**

- 根据压测结果调优连接池大小、超时时间、批量处理参数
- 识别并修复性能瓶颈（如锁竞争、GC 压力、网络序列化）
- 输出性能基线报告（`docs/benchmarks/performance_baseline.md`）

### Day 3：混沌工程故障注入演练

**演练场景**

- 节点宕机：随机 `kill -9` engine-go 实例，验证 service-hub 的任务重试与 audit-log 的写入不丢失
- 网络分区：模拟 app-lz 与上游服务网络中断，验证 BFF 层的降级响应
- 存储故障：模拟 PostgreSQL 不可用，验证 audit-log 降级到 SQLite 的正确性
- 慢依赖：模拟 engine-go 响应延迟 10s，验证 service-hub 的超时控制与熔断器行为
- 证书过期：模拟 mTLS 证书即将过期（< 24h），验证告警是否触发

**改进任务**

- 根据演练结果修复发现的容灾缺陷
- 补充自动化混沌测试脚本（`scripts/chaos/`）
- 输出混沌演练报告（`docs/chaos/chaos_engineering_report.md`）

### Day 4：生产监控看板与告警完善

**看板建设**

在 Grafana 中构建以下看板：

- 全局概览看板：各服务 QPS、错误率、P95/P99 延迟、健康实例数
- 网关流量看板：负载均衡分布、熔断器状态、限流触发次数
- 安全合规看板：mTLS 证书过期时间、API Key 使用情况、权限拒绝次数
- 存储看板：预算消耗进度、审计日志写入吞吐、任务队列深度
- 链路追踪看板：全链路调用拓扑、各阶段耗时分布、慢请求 Top 10

**告警规则**

补充 Prometheus Alertmanager 告警规则：

- P99 延迟 > 5s 持续 2 分钟
- 错误率 > 1% 持续 1 分钟
- 熔断器状态为 Open
- 预算消耗 > 80%
- mTLS 证书 7 天内过期
- 磁盘使用率 > 85%
- 任务队列积压 > 1000 且持续 5 分钟

### Day 5：生产就绪评审（PRR）与收尾

**评审清单**

逐项核验以下生产准入标准：

- 所有商业服务（engine-go、audit-log、service-hub）通过 72 小时稳定性压测
- 全链路追踪覆盖核心业务流程，可在 Jaeger 中查看完整调用链
- 监控看板与告警规则已部署并验证
- 混沌演练通过，系统具备自动容灾自愈能力
- 安全审计日志完整，满足等保三级追溯要求
- API 文档（OpenAPI/Swagger）已生成并部署
- 部署脚本（Helm/K8s）经过验证，支持一键回滚
- 运维手册（Runbook）已编写，包含常见故障处理流程

**交付物**

- 性能基线报告
- 混沌演练报告
- 生产就绪评审签署单
- 运维应急手册
- 全栈部署验证报告

## 关键风险与应对

**风险 1：AI 生成代码存在隐藏缺陷**

- 应对：对安全关键路径（认证、加密、预算扣减）进行人工逐行审查
- 应对：补充并发安全测试，暴露潜在的竞态条件

**风险 2：跨服务集成出现兼容性问题**

- 应对：第一周即启动全栈联调，尽早暴露集成问题
- 应对：统一错误码体系与日志格式，降低集成复杂度

**风险 3：性能瓶颈难以定位**

- 应对：从第一天起就启用 pprof 与追踪，建立性能基线
